# بانک اطلاعاتی امنیتی — مال خودمان

ساختن چیزی شبیه WPScan، به‌جای اجاره‌کردنش.

## چرا نه API دیگران

WPScan و Patchstack و Wordfence هر سه رفته‌اند سراغ کلید و سقف روزانه. با ۲۵
درخواست در روز نمی‌شود صدها سایت را پایش کرد. مهم‌تر: داده‌ای که اجاره کرده‌ای،
محصول تو نیست — روزی که قیمت را عوض کنند یا دسترسی را ببندند، قابلیت اصلی
محصولت از کار می‌افتد.

هر چیزی که لازم است، رایگان و بدون کلید در دسترس است. فقط باید جمع و نگهداری
شود.

## منابع — همه تأیید شده

| منبع | چه می‌دهد | هزینه |
|---|---|---|
| **NVD API 2.0** | ۱۷٬۶۰۰ CVE افزونه وردپرس، با شرح و شدت | رایگان، بدون کلید |
| **CVEProject/cvelistV5** | کل مخزن CVE، ۲.۳ گیگ، git clone | رایگان |
| **api.wordpress.org/plugins/info** | نسخهٔ فعلی، تاریخ آپدیت، حداقل PHP، وضعیت بسته‌شدن | رایگان، بدون کلید |
| **api.wordpress.org/core/checksums** | md5 هر فایل هسته | رایگان، بدون کلید |
| **Neo23x0/signature-base** | قوانین YARA شل‌ها | رایگان، MIT |

## معماری

```
  منابع بیرونی                 سرور ما                    سایت مشتری
  ─────────────                ────────                   ───────────
  NVD, cvelistV5     ──►  ingest job (روزانه)  ──►  فقط نتیجه، نه دیتا
  wordpress.org      ──►  جدول vulnerabilities
  signature-base     ──►  جدول signatures      ──►  پک امضا (نسخه‌دار)
                              ▲
                              │
                     سایت آلوده ──► نمونهٔ جدید ──► امضای جدید
```

نکتهٔ کلیدی: **سایت مشتری هرگز مستقیم به NVD یا گیت‌هاب وصل نمی‌شود.** همه‌چیز
از سرور ما می‌آید، پس نه ریت‌لیمیت می‌خوریم، نه IP مشتری‌ها جایی ثبت می‌شود، و
نه سایتی که آفلاین است از قافله عقب می‌ماند.

## جدول‌ها

### `vulnerabilities`

از NVD و cvelistV5 پر می‌شود، فیلتر شده روی اکوسیستم وردپرس.

```
cve_id          CVE-2024-xxxxx
slug            نامک افزونه در مخزن (کلید تطبیق)
kind            plugin | theme | core
version_from    اولین نسخهٔ آسیب‌پذیر
version_to      آخرین نسخهٔ آسیب‌پذیر
fixed_in        نسخه‌ای که وصله شده — مهم‌ترین ستون
severity        critical | high | medium | low
cvss            امتیاز عددی
summary         شرح کوتاه
published_at
source          nvd | cvelist | manual
```

**سخت‌ترین بخش، تطبیق نامک است.** CVE می‌گوید «WP Super Cache plugin before
1.7.2» ولی نامک مخزن `wp-super-cache` است. تطبیق باید ترکیبی باشد: CPE، عنوان
افزونه از wordpress.org، و در نهایت بازبینی انسانی برای مواردی که مطمئن نیست.
مورد مشکوک باید در صف بازبینی بیفتد، نه اینکه حدس زده شود — هشدار غلط روی
افزونه‌ای سالم، اعتماد کاربر را از بین می‌برد.

### `signatures`

بانک شل. سه منبع دارد و منبع سوم همان چیزی است که ما را از بقیه جدا می‌کند.

```
id
pattern         رشته یا الگو
kind            literal | regex | hex
severity        critical | suspicious
family          نام خانوادهٔ بدافزار
source          signature-base | community | ours
first_seen
sample_hash     هش نمونه‌ای که ازش استخراج شده
```

**منبع `ours` حلقهٔ بازخورد است:** وقتی روی سایت مشتری چیزی پیدا می‌شود که هیچ
امضایی نگرفته بودش، نمونه‌اش استخراج و امضای جدید ساخته می‌شود — و همان روز به
همهٔ سایت‌های دیگر می‌رسد. این چیزی است که خریدنی نیست: هر سایتی که مدیریت
می‌کنی، حسگر شبکه‌ات هم هست.

## چطور شل‌های *جدید* پیدا شوند

امضا فقط چیزی را می‌گیرد که قبلاً دیده شده. برای ناشناخته‌ها سه سیگنال که
مستقل از امضا کار می‌کنند:

**۱. فایل PHP جایی که نباید باشد.** `uploads/` هیچ‌وقت دلیل مشروعی برای داشتن
`.php` ندارد. این تنها سیگنال، اکثر شل‌های آپلودی را می‌گیرد — بدون هیچ امضایی.

**۲. آنتروپی و شکل کد.** فایل PHP با آنتروپی بالا، خط‌های خیلی بلند، نسبت بالای
کاراکتر غیرالفبایی، یا رشتهٔ base64 بلند. اینها obfuscation را می‌گیرند نه یک
بدافزار خاص را، پس روی نمونهٔ ندیده هم کار می‌کنند.

**۳. تغییر نسبت به خط پایه.** بعد از اولین اسکن سالم، هش هر فایل نگه داشته
می‌شود. فایل PHP تازه یا تغییریافته در افزونه‌ای که آپدیت نشده، به‌خودی‌خود
مشکوک است — همان منطق checksum هسته، تعمیم‌یافته به کل سایت.

سیگنال ۳ قوی‌ترین است و هیچ بانک اطلاعاتی لازم ندارد. برای همین باید زودتر از
بقیه ساخته شود.

## ترتیب ساخت

۱. **جدول‌ها و ingest job** — NVD روزانه، signature-base هفتگی
۲. **سرو کردن پک امضا** به سایت‌ها، نسخه‌دار، با ETag تا پهنای باند هدر نرود
۳. **تطبیق نسخه** — نصب‌شده در برابر `fixed_in`
۴. **خط پایهٔ هش** — سیگنال ۳ که از همه مؤثرتر است
۵. **حلقهٔ بازخورد** — نمونهٔ جدید از سایت آلوده به امضا تبدیل شود

## دو چیزی که باید صادق باشیم

**تطبیق خودکار CVE به نامک هرگز کامل نمی‌شود.** هر بانک آسیب‌پذیریِ تجاری هم
بازبینی انسانی دارد. مورد مطمئن خودکار، مورد مشکوک در صف بازبینی — نه اینکه
همه‌چیز حدس زده شود.

**پایگاه دادهٔ ما اول از رقبا عقب‌تر است.** WPScan سال‌ها داده جمع کرده. مزیت
ما جای دیگری است: حلقهٔ بازخورد از سایت‌های تحت مدیریت، که برای یک ارائه‌دهندهٔ
API وجود ندارد. این را باید در بازاریابی هم صادقانه گفت.
